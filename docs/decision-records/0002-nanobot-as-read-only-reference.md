# ADR 0002：把 nanobot 当作只读参照，而不是 fork

- 状态：已接受
- 日期：2026-09-17
- 关联：Phase 0（`.gitignore`）、Phase 1（源码理解）、Phase 2（核心代码迁移）

## 背景

项目目标是「基于 nanobot 的核心设计与部分实现做二次开发」。最省事的做法是 fork 后改包名，
但这与计划书原则二冲突（「不要直接复制整个 nanobot」），而且 fork 会让「哪些是我写的」变得不可解释。

## 决策

1. 上游源码只作为**读取参照**放在 `nanobot/`，整目录写进 `.gitignore`，不进入本仓库历史。
2. 迁移路径固定为：理解（Phase 1）→ 迁移最小实现（Phase 2）→ 重新抽象（Phase 3 起），
   每次迁移都要在阶段记录里说明「保留什么、改什么、为什么」。
3. 记录上游基线版本（v0.3.5 / `2fb165939`），所有架构描述都引用具体文件与行号，便于回查。
4. 许可与署名：上游为 MIT 许可，项目在 README 里明确致谢；后续若引入上游代码片段，
   需在该文件注明来源。

## 理由

- 面试与复盘的关注点是「为什么这样抽象」，只读参照能强迫每一步都用理由驱动，而不是顺着现有实现改。
- 不 fork 让本仓库的历史完全对应自己的工作过程，`git log` 本身就是一份过程证据。
- 上游是活跃仓库（2026-09-16 仍有提交），跟随上游 diff 的成本远高于独立实现的成本。

## 后果

- 没有上游的测试与 CI 兜底，本项目必须自己建立质量门（`scripts/check.sh`）与测试习惯。
- 上游的很多复杂度（多频道、TUI、WebUI、MCP OAuth 等）不会被继承，需要显式声明「本项目不做什么」，
  这部分写在 `PLAN.md` 的 2.2 节。
- 升级上游需要手动重读源码，代价可接受，因为只关心 Agent Runtime / Memory / Tool 这几块。
